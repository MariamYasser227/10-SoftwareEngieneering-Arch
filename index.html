Layered Architecture

N-tier

The system is organized into horizontal layers (e.g. presentation, business, data). Each layer only uses the services of the layer directly below it.

🤖

Real-life example

Android OS platform stack

Apps → Java API Framework → Native libraries & Android Runtime → Hardware Abstraction Layer → Linux kernel. The TCP/IP network stack follows the same idea.

Pros

  • Clear separation of concerns
  • Easy to test & maintain per layer
  • Layers replaceable / reusable

Cons

  • Performance overhead across layers
  • Changes may ripple through all layers
  • Can become monolithic

2
🖥️

Client-Server

Clients send requests to a central server that provides services or data and returns responses (e.g. web browser ↔ web server, email).

🌐

Real-life example

The World Wide Web & email

Browsers such as Chrome request pages from web servers such as Apache or Nginx over HTTP. Email clients (Outlook, Gmail app) talk to mail servers over SMTP/IMAP.

Pros

  • Centralized data & control
  • Easier security & backups
  • Thin clients, easy updates

Cons

  • Server is a single point of failure
  • Server can become a bottleneck
  • Network dependency

🗺️ Reference architecture

3
🕸️

Peer-to-Peer

All nodes are equal peers acting as both client and server, sharing resources directly without a central coordinator.

🧲

Real-life example

BitTorrent & Bitcoin

In BitTorrent, every downloader also uploads pieces of the file to other peers. Bitcoin nodes share transactions and blocks with each other without a central server.

Pros

  • Highly scalable
  • No single point of failure
  • Resources distributed among peers

Cons

  • Hard to secure & trust peers
  • Difficult to manage / back up
  • Inconsistent performance & availability

🗺️ Reference architecture

4
🔗

Pipe-and-Filter

Data streams through a chain of independent filters connected by pipes; each filter transforms its input into output (e.g. Unix pipes, compilers, ETL).

🐧

Real-life example

Unix/Linux shell & the GCC compiler

Shell commands are chained with "|" (cat | grep | sort). GCC runs source code through stages: preprocessor → compiler → assembler → linker.

Pros

  • Filters reusable & composable
  • Easy to add / reorder steps
  • Supports parallel / concurrent processing

Cons

  • Not suited for interactive systems
  • Data conversion overhead
  • Error handling across chain is hard

🗺️ Reference architecture

5
✉️

Messaging

Components communicate asynchronously by sending messages through a broker or queue (e.g. RabbitMQ, Kafka, JMS) instead of calling each other directly.

🛒

Real-life example

Amazon order processing & LinkedIn (Apache Kafka)

When you place an order, steps like payment, warehouse and shipping are handled through message queues (e.g. Amazon SQS). LinkedIn built Kafka to move trillions of messages a day between its systems.

Pros

  • Loose coupling of components
  • Reliable, buffered delivery
  • Handles load peaks well

Cons

  • Extra infrastructure (broker)
  • Harder debugging & tracing
  • Eventual consistency, latency

🗺️ Reference architecture

6
⚡

Implicit Invocation

Instead of calling procedures directly, a component announces an event; other components register interest and are invoked automatically when it occurs.

🖱️

Real-life example

Web browser DOM events & database triggers

JavaScript handlers registered with addEventListener("click", …) run automatically when you click a button. Database triggers (Oracle, SQL Server) run when a row is inserted or updated.

Pros

  • Strong decoupling
  • Easy to add new components
  • Supports reuse & evolution

Cons

  • No control over execution order
  • Hard to reason about correctness
  • Difficult to debug

🗺️ Reference architecture

7
📡

Publish-Subscribe

Example: Spotify

Publishers send messages to topics without knowing who receives them; subscribers receive every message for the topics they follow.

🎧

Real-life example

Spotify event delivery (Google Cloud Pub/Sub)

Every song play, skip or search is published as an event. Recommendation, royalty and analytics systems subscribe to these events. Spotify moved this pipeline to Google Cloud Pub/Sub in 2016.

Pros

  • Publishers & subscribers fully decoupled
  • Scales to many consumers
  • Subscribers added dynamically

Cons

  • Delivery / ordering guarantees vary
  • Hard to trace message flow
  • Topic / schema management overhead

🗺️ Reference architecture (Spotify-style)

8
🧩

Event-Based

Example: Eclipse IDE

Components produce and react to events. Eclipse plug-ins register listeners and extension points, reacting to editor, workspace and UI events.

🌘

Real-life example

Eclipse IDE (also VS Code extensions)

When you save a file, Eclipse fires a resource-change event; the Java builder, Git and error markers each react on their own. VS Code works similarly, loading extensions on "activation events".

Pros

  • Highly extensible (plug-ins)
  • Responsive, reactive behavior
  • Components developed independently

Cons

  • Complex, non-linear control flow
  • Testing event chains is hard
  • Risk of event storms / leaks

🗺️ Reference architecture (Eclipse-style)

9
🌐

Web Services

Functionality is exposed as services over standard web protocols (HTTP, SOAP/WSDL, REST/JSON), so machines can talk to each other across platforms.

✈️

Real-life example

Travel booking sites & the Google Maps API

Sites like Expedia and Skyscanner pull flight and hotel data from airline and hotel web services. Uber and many other apps call the Google Maps API for maps and routes.

Pros

  • Platform & language independent
  • Standard, interoperable protocols
  • Reuse of services across apps

Cons

  • Network latency
  • Payload overhead (XML/JSON)
  • Versioning & security challenges

🗺️ Reference architecture (SOA triangle)

10
⬡

Microservices

The application is built as a set of small, independently deployable services. Each owns its data and one business capability, and they talk via APIs or messaging.

🎬

Real-life example

Netflix

After a major database outage in 2008, Netflix split its monolith into hundreds of microservices on AWS (streaming, billing, recommendations), each deployed and scaled on its own. Amazon and Uber use the same approach.

Pros

  • Independent deployment & scaling
  • Technology freedom per service
  • Fault isolation

Cons

  • Distributed-system complexity
  • Data consistency is hard
  • High DevOps / monitoring effort
